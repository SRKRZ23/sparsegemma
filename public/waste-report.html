Why this happens — and why it's avoidable

Language is heavy-tailed (Zipf) and its vocabulary grows sublinearly with length (Heaps' law — we measure β≈0.75, R²=0.996 on 714k real tokens). So a whole conversation only ever needs a few hundred of a model's 100k–260k embedding rows. Yet every serving stack — Transformers.js, onnxruntime-web, llama.cpp, Google's own LiteRT-LM — downloads or memory-maps the entire table before the first token.

SparseGemma fetches only the byte ranges for the tokens actually used (HTTP Range requests), caches them across sessions, and — using the draft model already run for speculative decoding as a free prefetch oracle — hides the latency. On the hardest case (Gemma-4-E2B's 1.59 GB table) the live demo fetches hundreds of KB instead of gigabytes, with byte-identical output.

Honest caveat (we checked so you don't have to be surprised): in most of these models the embedding is weight-tied to the output head, so exhaustive full-vocabulary argmax still needs the whole table for the output projection. The clean win is on the input side universally, and on the output side too for separate-head exports or draft-guided / top-k generation. Full trace + math in the research folder — nothing swept under the rug.
